# 개발에서 확인한 학습 주제

## 2026-11-15 — release 이름·서명·실제 실행·공개 범위 구별

실제 release task와 non-debuggable·서명 verify·기기 설치를 각각 확인해야 하며 debug APK의 이름만 바꾸면 제출 조건을 충족하지 않는다. debug에만 HTTP 예외가 있으면 release는 같은 로컬 서버에 접속하지 못한다. source-set 한정 whitelist로 필요한 로컬 통신만 허용하고 다른 호스트의 차단을 유지할 수 있었다.

같은 package의 debug와 독립 release 서명은 업데이트 호환이 안 되므로 기존 앱 삭제 대신 별도 AVD가 유효했다. DPAPI 암호 파일 끝 개행과 native 도구의 한글 경로 실패는 APK/키 자체의 손상과 구분했다. 실제 없는 task를 추측해 성공했다고 기록하지 않고 task 목록과 debug 공통 코드 시험/release runtime 검증을 나눴다.

보안은 현재 main 파일만 보는 작업이 아니다. 닫힌 PR/원격 브랜치 이력·Git 작성자 metadata·SDK metadata 부재도 공개 범위에 영향을 준다. 소수초가 위치 regex에 잡힌 사례처럼 검색 후보는 문맥으로 분류해야 하며, 정적 검사 통과와 모든 권리/보안 문제의 부재는 다르다. 이는 이번 실행에서 확인한 원리이며 개인 학습 소감/추가 AI 자문을 만들어 기록하지 않는다. [증거](RELEASE_SUBMISSION_2026-11-15.md).

## 2026-11-14 — 빌드·서명·설치·실행·제출 가능성을 따로 확인

APK 생성 성공과 Gradle 전체 성공은 다르다. 이번에는 두 assemble/테스트가 성공한 뒤 개인 설정 표기 문제로 Lint가 실패했다. 원본 설정을 보존하고 동일 소스 사본으로 검사를 분리해 원인을 확인했다. debug 서명·SHA256·설치 성공도 release 배포나 서버 없는 동작을 보증하지 않는다.

기기 로그의 서버 brief 일치/onDone, 사람의 청취, 무음 화면 영상은 서로 다른 증거다. 부재중 청취 요청은 성공으로 기록하지 않고 실제 재생 후 사용자 응답을 확인했다. 고정 지역 날씨의 관측+1시간 TTL은 제출일을 넘겨 유지되지 않으므로 코드/APK 제출과 현재 데이터 가용성을 구분해야 한다. 이는 개인 학습 소감이 아니라 이번 검사에서 재현한 원리다. [실패·해결·검증](SUBMISSION_MVP_2026-11-15.md).

## 2026-11-13 — 취향 일치·검색어·행사 존재의 증거를 구분

구체 캐릭터 취향은 넓은 애니메이션 태그와 다르다. 검색에 사용한 단어가 반환 제목에 있다는 보장도 없다. 별칭/형식/제목 근거를 분리하고 ASCII 경계를 검사하자 party/art·chair/ai·limited/it 오탐과 검색어 태그 오염을 재현 가능하게 막을 수 있었다. 팝업 차단기와 팝업스토어도 문자 하나로 구별할 수 없어 문맥 조건을 사용했다. 제목에 드러나지 않는 취향과 새 별칭은 놓치는 한계가 남는다.

빈 추천은 생성으로 채울 문제가 아니다. 기존 실제97행에서 치이카와제목0이라는 관측과 공식 사업 포트폴리오의 사례는 현재 국내 행사 개최·좌표·취소 확인을 대신하지 않는다. ETA·장소 확인·수집 VERIFIED·TTS 허가는 서로 다른 증거다. 후속 기능 전에 이 차이를 계약에 적는 것이 앱의 잘못된 길안내를 막는 데 필요하다.

환경도 검증 대상이다. 같은 venv를 써도 editable 경로가 다른 checkout이면 현재 코드를 테스트하지 않을 수 있다. 실행 경로를 고정한 뒤 기존 중복 테스트 실패를 수정하고190개 회귀와 별도 Uvicorn HTTP를 확인했다. 테스트용 메타데이터 사례와 실제 콘텐츠 수집/차량 음성 증거를 분리했다. 이는 개인 학습 소감이 아니라 이번 코드/실행에서 확인한 원리다. [시도·실패·검증](DEVELOPMENT_LOG.md), [후속 한계](POPUP_ROUTING_RESEARCH.md).

## 2026-11-13 — 원천 관측·요청 위치·재생 범위를 구별

서버가 호출에 성공해도 관측시각이 오래되면 최신 날씨가 아니다. 수집시각으로 TTL을 연장하지 않고 원천 시각을 검사한다. 고정 POI009 자료는 내비 목적지와 무관하므로 지역 범위를 함께 전달한다. 권리 허가가 있어도 MVP가 정한 실음성 범위는 더 좁을 수 있어 공통 정책이 필요했다. 기존 LIVE 뉴스 음성 가정을 가진 테스트를 새 범위에 맞게 명시적으로 바꾸고 MOCK 회귀를 유지했다. 이는 AI가 추정한 개인 학습 소감이 아니라 코드·실행에서 확인한 설계 원리다. [증거·대안·한계](LIVE_WEATHER_DEMO.md).

## 2026-11-13 — 선택 프로필과 검색 조건·공식 공지와 사용 허가의 차이

같은 문자열 배열도 독립 취향 OR인지 특정 형식 AND인지에 따라 결과가 달라진다. 실제 지브리 메타데이터와 #9 matcher로 혼합 배열이 프로필 OR를 대체하지 못함을 확인했다. 기존 동작을 조용히 바꾸기보다 별도 입력 계약·구 서버404·빈 결과의 의미를 먼저 합의할 필요가 있다. 아직 구현하지 않은 인수 기준을 통과 테스트 수에 포함하지 않았다. [제안](INTEREST_PROFILE_PROPOSAL.md).

공식 공지에서도 날짜·장소·좌표·운영사·재사용 허가·최신 변경은 서로 다른 증거다. 현재 개최 공지를 찾아도 모든 요건이 해결되지는 않았고 공식 예매 공지 자체의 시간 충돌도 발견했다. 조회 실패와 검색 캐시를 현재 원문 성공으로 바꾸지 않고 실제 공공 API 수신5건으로 수집/차단 경로를 별도 확인했다. 무료 한도만으로 인증 준비·과금 비활성·차량 사용 허용을 증명할 수 없어 경로0회와 보류 이유를 남겼다. 이는 사용자 개인 숙련도에 대한 추측이 아니라 이번 관측에서 확인한 원리다. [출처](CONTENT_SOURCE_FOLLOWUP.md), [라우팅 조건](ROUTING_TRIAL_PROPOSAL.md), [실제 실행](DEVELOPMENT_LOG.md).

## 1. 자료의 타입·권리·유효성·추천 적합성은 다른 조건

**이해한 개념:** JSON이 모델에 들어맞는 것, 공식 API에서 수신한 것, TTS 권리가 있는 것, 지금도 유효한 것, 사용자의 경로와 관련 있는 것은 각각 별도의 판단입니다. 현재 코드는 권리 근거 없는 뉴스의 설명/음성을 막고 실데이터 행사 이동시간이 미검증이면 추천하지 않습니다.

**실제 확인:** 공개 API 자료의 수집은 성공했지만 행사5건은 이동시간을 몰라 제외됩니다. 뉴스 metadata 검증 상태가 VERIFIED여도 LICENSE_UNVERIFIED이면 음성 큐에 들어가지 않는 테스트가 있습니다. 테스트 fixture의 임의 질문도 실제 AI 답변으로 표시하지 않습니다. [권리/필터 테스트](../server/tests/test_recommendation.py), [출처 조건](DATA_SOURCES.md).

**발표에 사용할 경험:** “데이터를 확보하는 단계와 사용·재생할 수 있는 단계를 분리하고, 조건을 만족하지 못하는 항목은 명시적 이유로 제외했다.” 뉴스 라이선스를 확보했거나 AI 품질을 검증했다는 설명은 아직 할 수 없습니다.

## 2. 한 경로의 성공이 다른 경로의 일관성을 보장하지 않음

**초기 구현과 달랐던 점:** feed에서 오래된 교통정보를 제외했어도 상세 조회/설명에서는 허용됐습니다. 처음 코드에 유효성 검사가 있다는 사실만으로 전체 API에 적용됐다고 볼 수 없었습니다.

**어려웠던 부분:** expires_at은 미래인데 fetched_at은 오래된 교통정보를 구분하고, 기존 상세 조회·권리403·정확히10분 경계를 유지하면서 세 경로의 정책을 맞추는 일이었습니다. 임시 DB/고정 시각으로 재현한 신규10개 중6개가 먼저 실패했습니다. 공통 함수 적용 후 기존49를 포함해59개가 통과했습니다. [회귀 테스트](../server/tests/test_content_availability.py), 커밋 fdd7e2f.

**다음 개선:** 여러 endpoint가 같은 자료를 제공하면 최초부터 공통 도메인 조건과 경로 간 테스트를 준비합니다. 재생 직전 유효성 확인과 경로 적합성 검사는 별도로 유지합니다. **설명 가능한 핵심 경험:** 재현 조건→실패 테스트→공통 정책→회귀 확인의 순서로 결함을 수정했습니다.

## 3. HTTP200, 테스트 통과, 실차 연결은 서로 다른 증거

**이해한 개념:** 서버/DB health=ok는 모든 외부 제공자 정상이라는 뜻이 아닙니다. MockTransport 테스트는 원천 데이터 수신을 증명하지 않고, 로컬 Uvicorn HTTP 검사는 차량 앱/TTS 재생을 증명하지 않습니다.

**18시대에 확인한 차이:** 당시 pytest64는 모두 통과했지만 뉴스 키는 없고 학교 AI/실제 이동시간/실차 TTS도 미연동이었습니다. 이후 FreeNews 인증/일부 수신과99개 테스트까지 진행했지만 나머지 연동이 완료된 것은 아닙니다. 서울시 실제 호출과 MOCK/LIVE/MIXED HTTP 검사는 별도 보고서에 기록했습니다. 검사 도구도 빈 LIVE나 잘못된 모드를 실패로 남기도록 테스트했습니다. [18시대 집계와 검증 경계](verification/2026-11-11-revalidation.json), [후속 뉴스 조사](FREENEWS_INVESTIGATION.md).

**다음 개선:** 완료 기준을 코드/가짜 응답/실API/실기기 단계별로 작성하고, 성공 시각·입력의 성격·미검증 범위를 함께 남깁니다. **발표 경험:** “64개 자동 테스트와 실제 HTTP 검증을 수행했지만 실차 연결은 미검증으로 분리했다.” 숫자만으로 제품 완성을 주장하지 않습니다.

## 4. 응답이 있어도 앱용 계약은 불완전할 수 있음

**관측:** health/detail은 JSON을 정상 반환했으나 OpenAPI schema가 비어 있었습니다. 앱 담당자가 코드 없이 타입을 확인할 수 있는 상태는 아니었습니다.

**배운 원리와 적용:** 응답 모델을 명시해 실행 코드에서 OpenAPI를 생성하고, 기록된 명세와 런타임 명세가 일치하는지 검사했습니다. 입력 URL/JSON 필드를 유지하면서 계약을 보강했습니다. [계약 테스트](../server/tests/test_api_contract.py), [TD-01](TECH_DECISIONS.md#td-01-응답-객체를-코드와-api-계약의-공통-기준으로-사용).

**다음 개선:** 앱과 분업을 시작할 때 성공 응답뿐 아니라 null·빈 결과·403/404/409/422와 base URL을 먼저 공유합니다. 실제 기기 localhost/개발 PC 주소의 차이도 확인해야 합니다. 이 프로젝트의 Android 네트워크 설명은 공식 문서 기반이며 Pleos 기기에서 검증한 결과는 아닙니다. [연동 안내](VEHICLE_INTEGRATION.md).

## 5. 필드 이름뿐 아니라 시간·좌표의 의미를 확인해야 함

**기술적으로 어려운 지점:** 실제 AccInfo XML은 소문자 태그를 쓰고 시각은 HHMM/HHMMSS가 섞여 있습니다. 예를 들어 HHMM의1000은10:00이며 왼쪽을0으로 채운001000과는 다른 시각입니다. 현재 테스트는10:00KST=01:00UTC 변환을 확인합니다. GRS80TM 값도 위도/경도로 간주하지 않습니다.

**검증:** [제공자 테스트](../server/tests/test_providers.py)에서 관측 형태, 시각, 좌표 null, 원천 갱신일 미제공을 검사합니다. 등록일과 서버 수집일을 실제 수정일처럼 쓰지 않습니다. 동일 데이터셋 URL을 쓰는 서로 다른 교통 id를 합치지 않는 테스트도 있습니다.

**다음 개선:** 새 소스마다 원천 schema, 실제 응답 형태, 단위/시간대/좌표 체계, 필드 없음의 처리를 먼저 기록합니다. 전체 좌표 변환이나 미확인 enum을 추측해 구현하지 않습니다. **발표 경험:** “원천별 형식을 공통 모델로 정규화하면서 알 수 없는 값은 null/미검증으로 보존했다.” 아직 실제 지도 링크 매핑·라우팅 정확도를 검증했다는 설명은 하지 않습니다.

## 6. Mock은 분업을 계속하게 하지만 기능 완성의 증거는 아님

학교 endpoint가 없는 상태에서 LLMProvider와 저장 사실만 다루는 deterministic mock을 만들었습니다. 차량 담당자는 이 계약으로 화면/상세 흐름을 먼저 연결할 수 있습니다. 다만 Protocol 작성만으로 provider 교체가 끝나는 것은 아니며 현재 생성 코드에 실제 학교 API를 연결할 작업도 남아 있습니다.

MOCK/SIMULATED와 콘텐츠의 LIVE, 설명의 ai_mode를 구분해 실제 데이터가 있어도 AI는 Mock일 수 있음을 표현했습니다. [LLM 테스트](../server/tests/test_storage_popups_llm.py), [TD-06](TECH_DECISIONS.md#td-06-미제공-ai라우팅은-인터페이스와-mock으로-한정). 실제 모델 성능/환각률/음질 평가는 수행하지 않았습니다. 다음 프로젝트에서는 외부 인증/권리/실기기 접근을 초기에 확보하고, 실패 시 축소할 시연 범위를 먼저 정하겠습니다.

## 7. 성공한 검색0건과 실패/null은 다르며, 재시도에도 비용이 있음

FreeNews 인증 후 실제 JSON에서 SUCCESS의0건,5건,첫 페이지10건을 구분했습니다. has_more=true인10건을 전체 검색 수로 쓰거나24h/168h의 겹치는 결과를 고유 기사 수로 더할 수 없었습니다. 애니메이션500은 재현됐지만 오류 본문만으로 내부 원인을 단정하지 않았습니다.

더 긴 대기에서 과학 IT168h가10.844초 후 완료됐지만, 경과시간에는 연결 등이 포함되고 이전 timeout 단계는 없었습니다. read timeout과 전체 deadline을 구분해 설정하고 단계별 관측을 남겼습니다. 모든5xx 재시도 대신500은 제외하고 일부일시 오류에1회만 적용했습니다. GET 재시도도 할당량을 소모하므로 호출 예산과 백오프가 필요합니다.

검색/상세 하나의 실패가 성공 결과를 버리던 지점을 고치고, 중단 이전의 DB/JSON이 남는지 테스트했습니다. 실제 성공 목록을 재검색하지 않고 재사용해 상세2건만 보강한 점도 확인했습니다. **핵심 경험:** 관측 사실·미확정 원인·요청 성공/기사 수·권리 상태를 분리하고, 실패 격리와 제한적 복구를 구현했습니다. [조사/증거](FREENEWS_INVESTIGATION.md), [재시도 테스트](../server/tests/test_news_resilience.py), [자료 보존 테스트](../server/tests/test_news_jobs.py).

발표에서는 애니메이션500을 해결했다거나 실제 API 재시도 분기를 모두 검증했다고 말하지 않습니다. 실제 추가 호출은5회이며 재시도 분기는 MockTransport로 검사했습니다. 뉴스2건이 LIVE여도 권리는 미확인이라 음성/설명은 차단된 상태입니다.

## 8. API 계약 검사와 차량 오디오 출력은 서로 다른 완료 조건

서버와 같은 PC의 표준 AVD가 사용하는10.0.2.2는 그 PC의 loopback 별칭입니다. 팀원 PC의 AVD에서 이 주소를 써도 다른 PC에 있는 서버를 가리키지 않습니다. 실제 앱 HTTP·권한·SDK 초기화·합성/출력은 PC의 HTTP 성공과 나누어 검증해야 한다는 점을 접속 절차에 반영했습니다. Pleos 문서는 읽었지만 SDK를 실행한 것은 아닙니다.

서버의 TOP3/큐/alerts는 개수와 목적이 다릅니다. 실제 LIVE 화면3건 중 뉴스2건은 권리 미확인이었고, 음성 큐는 실제 날씨1건뿐이었습니다. 화면 카드를 그대로 낭독하면 권리 검사를 우회하게 됩니다. 재생 후보와 권리 근거를 확인하고, 재생 직전의 유효성도 확인하도록 안내했습니다. 실제 TTS 출력이 없더라도 이 서버 측 경계는 HTTP와 회귀 테스트로 확인할 수 있습니다.

검사 도구의 성공 조건도 테스트해야 했습니다. 후보 집합에 속한다는 확인만으로 재생 순서의 누락·역전을 검출할 수 없어 전체 순서와 긴급 항목을 검사했습니다. 추가 테스트에서는 특정 뉴스가 항상 TOP3일 것이라는 가정을 버리고 잘못된 응답 조건을 직접 구성했습니다. 시연 데이터는 원천 기준시각으로 만료되므로 과거 성공 숫자보다 현재 자격/신선도가 중요합니다. [TD-10](TECH_DECISIONS.md#td-10-서버-http-준비와-pleos-기기tts-완료를-따로-판정-2026-11-11), [측정/검증 경계](verification/2026-11-11-vehicle-handoff.json).

발표에서 설명할 수 있는 경험은 "실자료와 모의 자료를 구분하고 API·권리·유효성·기기 단계를 각각 판정하도록 인계했다"입니다. 실제 Pleos 연결·음성 출력·실차 안전 UX를 완료한 경험으로 말할 수는 없습니다.

## 9. 기본 상태값을 취소로 해석하거나 페이지 메타를 간격으로 사용하면 자료를 잃음

TourAPI에서 HTTP200/10건 수신만으로 유효 행사를 확보한 것은 아니었습니다. 공식 매뉴얼의 선택안함을 truthy 검사로 제외해 예정 행사도 버렸습니다. 상태 필드의 이름만 보고 진행 중/예정 enum으로 가정하지 않고 원천 문서·실응답·날짜를 함께 확인했습니다. 미확인 온라인1건도 취소라고 단정하지 않았습니다.

실제 마지막 페이지 numOfRows가 요청 크기50이 아닌 반환27이어서 페이지 번호와 곱하면 잘못된 다음 호출이 발생했습니다. 누적량과 총수를 비교하는 회귀 테스트로 고쳤습니다. 오늘 범위 요청에 오래전에 시작한 진행 중 행사도 포함돼 검색 시작일과 행사 시작일이 항상 같다는 가정도 버렸습니다. 이 관측을 모든 입력 조합의 검색 의미로 확대하지 않았습니다.

기간/권리/차량 이동시간은 서로 다른 자격입니다. 날짜 유효76건을 저장했어도 Type3이고 라우팅 미검증이라 추천·TTS 완료로 표시할 수 없었습니다. 원천 종료일과 수집 시각을 분리하고 새 취소 관측은 기존 데이터를 삭제하는 대신 검증 상태와 관측 이력에 반영했습니다. 다음 소스 연동에서도 기본값·마지막 페이지·기간 경계를 초기에 실제 작은 표본으로 확인해야 합니다. [근거/측정](TOURAPI_INVESTIGATION.md).

## 2026-11-11 — 앱 계약 검증과 기기 검증의 경계

실제 서버 JSON을 Android에서 쓰는 동일 HTTP/파서 코드로 검증하면 필드/null/순서 오류를 조기에 찾을 수 있습니다. 그러나 JVM 테스트는 Android의 평문 HTTP 정책이나 TTS 서비스 상태를 검증하지 않습니다. 이번에는 HTTP 통합/두 flavor 빌드가 성공했어도 에뮬레이터 자체의 SIGILL로 화면·음성 실행은 확인하지 못했습니다.

패스·다시 구현은 단순 인덱스 변경으로 끝나지 않습니다. 이전 HTTP/SDK 콜백이 늦게 도착할 수 있으므로 coroutine 취소, 재생별 SDK 수명, 포커스 해제 후 콜백 무시를 함께 적용했습니다. 자동 테스트는 취소·권리 변경·사라진 항목·새 빈 피드·통신 실패를 검증했지만 실제 기기의 SDK 이벤트 순서/오디오 지연은 남은 측정 항목입니다. [검증 기록](verification/2026-11-11-vehicle-app.md).

## 2026-11-13 — 콜백, 실제 안내, 데이터 provenance의 검증

단위 HTTP 성공만으로 실제 NaviHelper 목적지 수신을 증명할 수 없었다. 실제 기본 내비에서 안내를 시작한 뒤 SDK 상태·앱 표시·서버 요청을 연결해 확인했다. SDK3.0.5와 서비스 응답은 버전·권한·Nav 앱 상태의 영향을 받았고, 조회 권한과 목적지 생성 권한은 달랐다. 원천 GPS 시각 미제공을 receivedAt으로 보완해도 원천의 신선도가 생기는 것은 아니다.

차량 위치와 다른 고정 지역의 날씨라도 지역/시각을 명시하면 한정된 실자료 시연이 가능하다. 서버와 앱의 공통 방어·만료/연결 실패 신규TTS0 검사로 허가된 최신 brief만 읽는 것을 확인했다. MOCK을 별도 표시해 유지했고 잡음과 기능 연결의 완료를 분리했다. 개인 학습 감상을 추정하지 않고 실제 문제·시도·성공/실패 근거는 [2026-11-13 기기 검증](verification/2026-11-13-live-weather-vehicle.md)에 기록했다.
