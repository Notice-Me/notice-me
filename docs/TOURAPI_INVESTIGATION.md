## 공식 명세와 상태값

[공공데이터포털 공식 상세](https://www.data.go.kr/data/15101578/openapi.do)의 Swagger와 첨부 활용매뉴얼 국문 v4.4를 확인했습니다. 첨부 파일과 schema hash는 측정 JSON에 기록했으며 원문 매뉴얼 전체는 저장소에 올리지 않았습니다.

- searchFestival2의 pageNo/numOfRows, eventStartDate/eventEndDate와 arrange를 확인했습니다. arrange의 A/C/D는 각각 제목/수정일/생성일 기준이며 날짜상 시작순을 요청하는 옵션으로 가정하지 않습니다. 이미지를 요구하는 O/Q/R 대신 C를 사용합니다.
- 매뉴얼의 progresstype 응답 예시는 **선택안함**입니다. Swagger는 취소·행사연기 정보로 설명합니다. 이를 일반 진행 중/예정 enum이나 숫자 코드로 해석하지 않습니다.
- 빈 값/선택안함은 이 필드에 취소 표시가 없는 것으로 처리합니다. 취소/행사연기는 제외하고 알 수 없는 값은 UNKNOWN_PROGRESS_TYPE로 보류합니다. 전체 enum 목록이 제공됐다고 주장하지 않습니다.
- 실제 새77건에는 선택안함71, 빈 값5, 온라인1이 있었습니다. 온라인은 문서상 festivaltype 설명에도 등장하지만 실제로는 progresstype에 들어왔습니다. 필드를 임의로 옮겨 정상/취소로 확정하지 않고1건을 보류했습니다.

## 날짜·정렬·페이지 정책

KST 오늘부터 +90일까지 요청하고, 서버에서도 **원천 시작일≤범위 끝 / 원천 종료일≥오늘**을 검사합니다. 종료일은 해당 KST 날짜의 다음 날00:00에 만료됩니다. 진행 중/예정은 날짜 기준 분류이며 매일 운영시간·입장 가능 여부를 보증하지 않습니다.

실제 요청 범위는20261111~20270209였습니다. 이전에 시작한 진행 중36건도 반환됐고 가장 이른 시작은2022-11-01, 범위 끝보다 나중에 끝나는 항목도4건 있었습니다. 따라서 eventStartDate를 단순한 "원천 시작일 하한"이라고 해석해 과거365일 등을 임의로 넓힐 필요가 없었습니다. 문서의 날짜 설명만으로 모든 입력 조합의 검색 의미를 확정하지 않고 이 기간 겹침 관측과 로컬 검사로 검증 범위를 한정합니다.

페이지 크기 기본50, 최대3페이지·최대3시도, 요청 간격1초, 자동 재시도0회입니다. 앱 자체 설정 상한은 페이지 크기100·페이지/시도10·미래180일이며 제공자의 최대 허용값이라는 뜻은 아닙니다. 공식 개발 트래픽 표시는1,000이지만 사용자 계정의 승인량/현재 잔여량은 조회하지 않았습니다. 유료 전환이나 전체 무제한 수집은 없습니다.

첫 개선 수집은50+27건을 받았으나 마지막 응답 numOfRows=27을 페이지 간격으로 사용해 불필요한3페이지 요청이 발생했고 SCHEMA_MISMATCH로 PARTIAL이 됐습니다. 실제 마지막 응답 필드와 요청 크기를 혼동한 문제입니다. 종료를 누적 raw 수신량/totalCount로 바꾸고 회귀 테스트를 추가했습니다. 수정 후2회 상한으로 다시 호출해50+27에서 종료했습니다. 중복/total 변경/예산·페이지 한도/빈 페이지 불일치는 PARTIAL로 표시합니다. complete는 이 검색창의 관측 페이지 범위이며 모든 행사·취소 상태의 완전한 스냅샷 보증이 아닙니다.

| 항목 | 최종 관측 |

| 데이터 호출 | 2회, page1=50 / page2=27, page3 미호출 |

원천 createdtime은 등록일, modifiedtime은 원천 수정일, fetched_at은 수집 시각, expires_at은 행사 종료일에서 도출합니다. 수집했다고 종료일을 늘리지 않습니다. published_at에 원천 등록일을 매핑한 기존 규격은 유지하며 실제 행사 발행일이라고 확대 해석하지 않습니다. 원천 행사 타입15는 EVENT로 보존합니다. 전시를 포함할 수 있지만 별도 전시 세부분류나 문화시설14 전체 수집을 구현한 것은 아닙니다.

**현재 LIVE 행사는 실제 자동차 이동시간 검증이 없어 추천에서 계속 제외됩니다.** 날짜 유효76건이 곧 추천76건/TTS76건은 아닙니다. Type1만 기존 권리 근거로 음성 자격을 부여하고 Type3/미확인은 차단합니다. 실차 경로·길찾기·TTS를 실행한 검증도 아닙니다. 실제 원천 HTTP와 내부 ASGI 검사를 구분합니다.

## 저장·재현·회귀 검사

각 페이지의 원천 id/시작·종료/상태/권리·제외 사유를 event_pages에 저장합니다. 성공 항목은 다음 요청 전 SQLite에 commit합니다. 후속 실패/중단이 앞선 페이지를 지우지 않습니다. 새로 취소·만료·불명확 상태가 관측된 기존 id는 삭제하지 않고 UNVERIFIED로 격리합니다. 단순 범위 밖/미수신은 취소로 가정하지 않습니다. 이는 전체 동기화/자동 스케줄러를 대신하지 않습니다.

server 폴더에서 아래 명령은 **실행할 때만 실제 할당량을 소비**합니다. 기존 .env는 덮어쓰지 않습니다.

```powershell
.venv\Scripts\python.exe -m app.cli ingest --public-provider tourapi --report reports/tourapi-next.json
.venv\Scripts\python.exe -m pytest -q
```

NOTICE_TOUR_PAGE_SIZE=50, NOTICE_TOUR_MAX_PAGES=3, NOTICE_TOUR_REQUEST_BUDGET=3, NOTICE_TOUR_LOOKAHEAD_DAYS=90으로 조정합니다. 뉴스용 --max-requests와는 별도 예산입니다. 마지막 실검증은 프로세스 환경에서 Tour 예산만2로 제한했습니다.

[테스트](../server/tests/test_tour_collection.py)는 기본값/취소/연기/미확인 enum, KST 날짜 경계, 종료·필드 오류별 사유, pagination/마지막 numOfRows, 중복·변경 total, 예산/timeout/게이트웨이 오류, 페이지 보존/취소 격리, 권리·LIVE 라우팅 차단을 MockTransport로 검사합니다. 최종147개 통과이며 이 숫자를147회 실제 API 성공으로 해석하지 않습니다. 실제 호출 이후 숫자0 상태를 빈 값으로 잘못 처리하지 않도록 방어 코드를 추가했고 해당 분기는 mock으로 검사했습니다. 추가 네트워크 반복은 하지 않았습니다.
