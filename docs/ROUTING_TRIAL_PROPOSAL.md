## 제안하는 최소 시험

1. 우선 후보는 REST 규격과 쿼터를 확인한 카카오다. 사용자가 기존 무료 앱/키를 갖고 있는지와 적용 가능한 사용 목적을 확인한다. 필요하면 사용자가 계정에 로그인해 무료 잔여량·서비스 권한·결제/유료 쿼터 비활성 상태를 확인한다. 키는 채팅/PR에 붙이지 않고 로컬.env에만 보관하며 기존 파일 전체를 덮어쓰지 않는다.
2. 새 인증·등록·약관 동의 또는 결제가 필요하면 그 작업과 조건을 사용자에게 보고한 뒤 별도 승인 범위를 정한다. 유료 전환/과금 위험이 해소되지 않으면 호출하지 않는다. 계정/유료 설정이 이미 확인됐다고 가정하지 않는다.
3. 사용자 실위치 대신 공식 공공 API의 검증 가능한 공개 시설 좌표 한 쌍으로 검증한다. 이번 수신 영등포아트홀 좌표는 사용할 수 있는 후보지만 실제 차량 출입구와 일치하는지 별도로 확인해야 한다. 무민/치이카와의 미확인 좌표를 만들지 않는다.
4. 한 제공자·정상 요청1회부터 시작, 전체 요청 예산은 오류 포함 최대5회, 자동 재시도0. 401/403/429/한도·결제 요구/비정상 응답이면 멈춘다. timeout·실패 파싱은 MockTransport로 검증할 수 있으므로 외부 오류 호출을 일부러 반복하지 않는다. 앱15초 feed 요청이 매번 외부 라우팅을 호출하는 구조를 만들지 않는다.
5. 요청 성공과 result_code·실제 경로·좌표 쌍·유한한 양수 duration의 일관성을 확인한다. 카카오의 경도,위도 순서와 duration 초 단위를 지키고 minutes=duration/60으로 비교한다. 3,601초를 내림해60분으로 허용하면 안 된다. 미검증 값이나 목적지 ETA는 대체값으로 쓰지 않는다.
6. 실제 성공과 요청/오류 횟수·제공자·검사 시각·만료 정책만 보고하고 키/원본 전체 경로/정밀 사용자 좌표 이력은 저장·커밋하지 않는다. 최초 시험은 캐시 없이 요청 중 처리한다. 재사용/장기 보존은 공급자 이용조건과 개인정보 범위를 확인한 뒤 설계한다.

## 기존 RoutingProvider 연결 조건

후속 구현은 feed 요청의 비동기 단계에서 검증 후보만 제한적으로 평가한 후, 요청 수명 안의 평가 결과를 동기 추천에 주입하거나 인터페이스를 명시적으로 async로 바꾸는 방안을 검토한다. 실행 중 event loop 안에 asyncio.run을 넣지 않는다. 추가 API 응답 필드는 필요하지 않고 기존 TravelAssessment의 status/minutes/provider/checked_at을 재사용할 수 있다. 서버가 실제 검증한 경우만 VERIFIED, 그 외 UNVERIFIED 유지다. 시뮬레이션은 MOCK/SIMULATED만 허용한다.

위치를 공개 시설로 시험해 API가 성공해도 특정 사용자의 행사장60분 조건을 검증한 것이 아니다. 실제 후보에 쓸 때는 **요청의 출발지와 해당 행사 장소**의 경로를 검증하고 유효기간·차량 접근·종료 전 도착을 확인해야 한다. 호출 예산 부족/권한·약관 미확인·자동차 이동시간 미확인은 기존 진단으로 제외한다. 이번에 수신한5개 공공 행사도 실제 경로가 없어 LIVE 추천/음성0을 유지했다.
